## Consumption authority and exact state boundary

The challenge remains selected by the existing exact user/code/target lookup, with targetValue when provided. Keep existing safe prechecks/errors: absent record 404 `OTP_NOT_FOUND`, already verified 400 `OTP_ALREADY_VERIFIED`, expired/invalid/missing expiry 400 `OTP_EXPIRED`, unequal code 400 `INVALID_OTP`. Expiry equality is expired; malformed/missing expiry must never provide a proof. Do not introduce a reserved-code blacklist or a test bypass.

Before mutation, require the selected record to have a nonempty string `targetValue` (whitespace-only is invalid). If a caller supplied `targetValue`, it must equal the selected stored value exactly. A bound record selected without a supplied value by an existing email-verification caller remains usable; the mutation pins its exact stored destination. A bound login lookup excludes legacy unbound or mismatched destinations and retains the existing 404 `OTP_NOT_FOUND`; do not add a fallback or widen that lookup. If an existing optional-target email-verification caller actually selects an unbound record, return 400 `OTP_UNAVAILABLE`, with the fixed safe message `OTP is no longer available; request a new OTP`. Both paths deny proof and retain the existing send endpoints as the fresh resend path. Do not infer an old recipient from the current user's address or backfill historical challenge data.

Preserve the existing **verification-service clock** policy. After the existing prechecks, snapshot the selected challenge's exact identity/proof/destination and valid expiry Date value. Change the internal repository consumption signature to accept the selected challenge ID, the exact verification request with required bound targetValue, the observed expiry, and a fresh service-clock Date captured immediately before consumption. One conditional `findOneAndUpdate` must match **all** of `_id`, `userId`, `otp`, `target`, exact `targetValue`, `isVerified:false`, and `expireAt` satisfying both `$eq: observedExpiry` and `$gt: consumeCheckpoint`. The explicit command payload sets only `isVerified:true`, and explicitly returns the updated document (`new:true`); existing model-managed timestamps such as `updatedAt` may change as before. These are existing portable query operators and Date values; do not introduce `$expr`, `$$NOW`, a production MongoDB version decision or a new clock policy.

The equality predicate binds the expiry observed with the proof: changing/refreshing that record's expiry or identity/proof/destination between lookup and consumption must make the original contender lose. The greater-than predicate rejects expiry at the pre-consumption service checkpoint. After a successful update resolves, revalidate the returned expiry as a finite Date strictly later than a fresh service-clock Date **immediately before returning the proof**, with no intervening asynchronous step. If this final check fails, throw the existing 400 `OTP_EXPIRED`; leave the challenge consumed and require a fresh send, without rollback or a proof/JWT. Missing/malformed expiry also fails closed. This final OTPService checkpoint is the verification acceptance point; the contract makes no database-clock, network-latency, wall-clock-at-commit or eventual-JWT-issuance deadline guarantee.

The first successful mutation returns the verified document. If the conditional mutation returns null because another request consumed/deleted/changed the challenge or its expiry no longer passes the consumption checkpoint, return 400 `OTP_UNAVAILABLE` with the same fixed safe resend message; do not return a proof or expose which concurrent condition occurred. Actual database errors propagate through the existing error path. No second lookup is necessary to diagnose the losing race.

`AuthService` must await successful consumption **and the final live-proof checkpoint** before any user update, wallet creation, notification or JWT. Its existing order already does so and remains unchanged. At most one contender for the **same challenge record** may advance. This is not an account-wide lock across distinct simultaneously issued challenges; resend/create races remain separate work.

## Login destination binding

In the existing login verifier, retain phone precedence when both fields are supplied (the current schemas use `.or`, not `.xor`). After the existing identity lookup and inactivity checks, derive `target` from that same phone/email selection and derive the canonical destination from the corresponding **loaded identity record**: trimmed phone or trimmed/lowercased email. Require a nonempty selected destination; otherwise return the same safe 400 `OTP_UNAVAILABLE`. Pass this `targetValue` to `OTPService.verifyOTP`. This binds the proof to the server-selected identity's contact rather than accepting any same-user email/phone-target challenge. It does not authorize or repair contact changes; a concurrent contact change after identity lookup remains within that separate lifecycle contract.

Keep public send and dedicated email-verification logic otherwise byte-identical. Normal generated phone/email logins and both email-verification APIs remain supported. No secret/code/expiry chosen by an HTTP caller is promoted into a valid challenge through a new route or flag.
