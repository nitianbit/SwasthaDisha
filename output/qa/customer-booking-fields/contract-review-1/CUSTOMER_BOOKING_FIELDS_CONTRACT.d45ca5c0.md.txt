## Exact current behavior and why a separate narrow service path is needed

The graph discovers BookingController/BookingService in project swasthadisha but remains indexed against the original checkout at bfb608e; its inbound update trace returned no callers. Exact current files and the already verified specialist caller are authoritative, not graph absence.

- Authentication mounts before the bookings router. PUT /api/v1/bookings/:id runs params validation, shared update-body validation, query validation, then BookingController.update.
- The controller already resolves signed ownership using resolveBookingOwnerScope before ensureHRReadOnly and calls BookingService.update(id, body, owner). Reuse that helper unchanged; do not create another actor/owner resolver.
- UpdateBookingRequest and shared update Joi admit corporateId, slot/date/time/mode/address, documents, prescription, report, followUp, primaryConcern, consultationMode, contacts, status, paymentStatus, notes and cancellationReason. The internal DTO also contains lifecycle, cancelledAt and virtualMeeting; Joi does not directly admit those three.
- The shared validator uses abortEarly:false and stripUnknown:true, then replaces req.body. Unknown input is not a reliable raw-body rejection boundary. Existing invalid-field value errors occur before controller authorization.
- BookingService.update first performs getById(id, owner), then derives lifecycle/payment fields and writes with only {_id:id}. A notes-only call on an already cancelled booking still invokes ensureCancelledBookingPaymentStatus, which can mark payment refunded, then clears reminders/cancels meetings. A concurrent completion can also select completion/follow-up effects. An allowlist followed by this unchanged generic algorithm would not establish a notes-only mutation.
- SpecialistPortalService.updateAppointmentStatus calls the shared update without a customer owner. Preserve this signature and its behavior; do not globally restrict its DTO or shared Joi. Preserving it is not certification of specialist/admin/other-role authority.

## Exact ordinary-customer rule and operation order

An ordinary customer is exact authenticated userType === 'user', using the signed _id unchanged. Ownership is not patient/dependent consent. The existing resolver supplies the owner and preserves its precedence:

1. Existing upstream JWT/params/body/query validation remains unchanged. Missing/expired/invalid JWT and existing 400 VALIDATION_ERROR outputs retain their present order/messages.
2. resolveBookingOwnerScope retains controller 401 UNAUTHORIZED / Authentication is required for malformed actor, then 403 FORBIDDEN / Access to bookings owned by another user is not permitted for a nonmatching supplied query owner. These happen before any booking service call. ensureHRReadOnly retains 403 FORBIDDEN / HR has view-only access to bookings for exact HR.
3. Exact customers dispatch once to updateCustomerNotes with the exact signed owner. Other actors dispatch once to unchanged generic update. No preliminary unscoped read or fallback is introduced.
4. The new service operation requires a nonblank string signedOwner at runtime. Absent/nonstring/blank scope rejects 401 UNAUTHORIZED / Authentication is required before any repository call. This is a required-scope parameter check, not a second request-actor implementation. Do not coerce or trim the owner used in predicates.
5. Validate the data once before persistence, in this order: first require a non-null, non-array plain object (Object.prototype or null prototype), otherwise fixed400 below; next reject any own key other than notes with 403 CUSTOMER_BOOKING_FIELDS_FORBIDDEN / Only booking notes may be changed through this endpoint; then require the one own notes property and a valid string/length, otherwise fixed400. Enumerate all own keys, including symbols/non-enumerables, rather than trusting a structural type. Fixed400 is VALIDATION_ERROR / Customer booking updates require notes containing 1 to 2000 characters. No key/value echo, silent service-side stripping, mutation of the supplied object or reuse of a caller object as Mongo update data. Prototype-bearing DTO/document instances are invalid, not a supported bypass. JSON cannot supply symbols, non-enumerables or custom prototypes; those checks protect direct internal invocation, not an extra HTTP-format claim.
6. Trim the string using ordinary JavaScript trim, matching existing note normalization; require length 1 through 2000 JavaScript UTF-16 code units after trimming. Store that normalized value. No number/boolean/object-to-string conversion or null/empty deletion. This is the deliberate new bounded-note compatibility rule; the shared Joi and other roles/endpoints retain their existing rules. A full replacement is intended; note histories/optimistic version conflict detection are not invented here.
7. Perform exactly one existing getById(id, signedOwner), whose combined {_id:id,userId:signedOwner} lookup yields existing 404 BOOKING_NOT_FOUND / Booking not found for foreign/missing IDs. No private business/patient lookup is needed.
8. Require stored status pending or confirmed. Missing, unknown, completed or cancelled status rejects 409 CUSTOMER_BOOKING_NOT_EDITABLE / Booking notes cannot be changed in the current state. Define this eligible status set once and reuse it for both the check and final predicate; no payment status, amount, date or future state is inferred from the note request.
9. Perform exactly one BookingRepository.update using {_id:id,userId:signedOwner,status:{$in:eligibleStatuses}} and a newly constructed {$set:{notes:normalizedNotes}}, with new:true and upsert:false. Never spread data/booking into it. Never forward an operator/replacement/lifecycle supplied by the caller. Existing model timestamps may update updatedAt; no other business field is part of this write.
10. A null final update (concurrent deletion, owner/state change or other nonmatch) rejects the same fixed 409 CUSTOMER_BOOKING_NOT_EDITABLE; do not retry, upsert, re-read another owner, call generic update or perform effects. Database errors propagate through existing middleware. On a matching write return that updated booking directly, once, without deriving lifecycle, clearing/scheduling reminders, activating follow-up, syncing/cancelling a meeting, changing slot capacity, payment/wallet/coupon state or dispatching notifications/providers.

The final owner/status predicate prevents this operation from writing after a now-ineligible owner/state change. It does not make the shared generic update/delete/cancel/reschedule paths atomic, implement a cross-command transaction, prove revocation/current account state, or provide note version history. Concurrent eligible note replacements remain last-writer-wins. A complete remove/recreate/ABA or application-wide author/history policy is outside this bounded containment.

## Field and validation compatibility

| Effective ordinary-customer input after existing Joi | Decision before booking lookup |
| --- | --- |
| Exactly notes with a valid bounded string | Continue to owned lookup/state check/restricted write. |
| Any admitted non-notes key, alone or mixed with notes | Fixed 403 CUSTOMER_BOOKING_FIELDS_FORBIDDEN, including corporateId, slotId, bookingDate, bookingTime, serviceMode, serviceAddress, documents, prescription, report, followUp, primaryConcern, consultationMode, contactNo, alternateContactNo, status, paymentStatus or cancellationReason. Equal-to-current values are still forbidden. |
| Empty/invalid shared Joi body or invalid admitted-field value | Existing 400 VALIDATION_ERROR from Joi before controller; do not promise a field-policy 403 for a body Joi already rejects. |
| Notes too long after trim | New operation's fixed 400 VALIDATION_ERROR, no booking lookup. Empty/nonstring notes usually fail shared Joi first; direct service invocation must also fail closed. |
| Unknown raw fields such as price, originalPrice, userId, dependentId, pharmacyId, bookingType, paymentTransactionId, lifecycle, cancelledAt, virtualMeeting, createdAt, updatedAt or Mongo/dotted operators | Existing middleware strips unknown fields. If valid notes survives, only notes can be written; an otherwise empty result fails existing Joi min(1). A valid surviving forbidden field still gets 403. Do not falsely claim all raw unknown keys produce 403. Direct service calls containing these keys must reject. |

Keep stripUnknown behavior rather than widen the shared validation change. The guarantee is the closed effective write set and rejection of surviving privileged fields, not detection of every raw attempted key. No customer-controlled owner, money, corporate affiliation, lifecycle, clinical authorship/release or meeting state reaches the new write. Ignoring a stripped attempted field is not permission to change it. Test the actual installed Joi path later instead of deriving HTTP conversion/unknown/min behavior from a direct service fake.

Success retains HTTP200 {success:true,message:'Booking updated successfully',data:result}. Error serialization stays {error:statusCode,message,code}. No new response shape, redirect or extra authentication flow. Returned booking follows the existing owned-booking projection; this slice adds no log/event and does not certify every legacy returned field or downstream rendering of untrusted free text.

Examples use a valid owned pending/confirmed booking ID and omitted/self query owner:

- PUT /api/v1/bookings/:id with {"notes":" Please use the entrance on the left "} stores trimmed notes and returns the existing 200 envelope.
- {"notes":"My request","paymentStatus":"paid"}, {"status":"cancelled"}, {"prescription":{"message":"approved"}}, {"contactNo":"9876543210"} or a well-formed corporateId receives 403 if the existing Joi first accepts the supplied values. No booking lookup/write/effect follows.
- {"notes":"My request","price":1} retains legacy raw-key stripping and can update notes only; price is unchanged. {"price":1} must be measured through existing Joi and is expected to fail min(1), never become a price write.
- The allowed note request for another account's ID gives 404; a foreign query userId gives early403 even if the resource is missing. A terminal owned booking or lost final predicate gives fixed409.
- Use the existing POST /:id/cancel and POST /:id/reschedule surfaces for their respective requests. Their safety, capacity/refund semantics and clinical/financial acceptance are not certified or bypassed by this contract. Generic PUT cannot substitute status/date/slot changes for those operations.

Legacy customer clients using generic PUT for status/payment/clinical/contact/logistics fields will intentionally receive denial instead of their previous privilege. Do not silently translate such payloads into cancellation/rescheduling or claim supported-client acceptance without inventory and actual tests. Large notes and terminal-booking note edits also intentionally stop working. Noncustomer generic behavior and specialist updateAppointmentStatus remain byte-preserved, including their unresolved authorization/finance/clinical risks; unknown nonempty signed roles are not newly approved. Create, direct clinical/file writes, own DELETE, contact identity and cancellation/reschedule/retry-money defects remain separate open work.
