# Review prompt contract and evaluation notes

**10 November 2026. Author-side Prompt Optimizer package; excluded from reviewer inputs.**

## Target and success criteria

New portable user-message prompt for Claude Code/other coding agents, snapshot unspecified. Platform/deployer owns tool authority; task prompt owns read-only review scope and output shape. Documents supply evidence only. Success is an actionable decision about the first isolated no-DB smoke, with source/evidence verification and retained C2/C3/domain gates. No new general implementation-start approval is requested.

## External context

Loaded by author: current AGENTS/approval/progress, controller/protocol/fixtures/unit runner, all new TAP/canary logs, public image manifest metadata, known local-engine observation and primary Docker/Node documentation. Referenced for reviewer: six exact input groups in the prompt. Out of scope: operational resources, patient/credential files, real SDK/app entry execution and unrelated architecture redesign.

## Eval cases

| Case | Required behavior | Failure |

| Historical hash differs after intentional runner revision | Use correct baseline and current frozen manifest | Call all current work invalid based on old snapshot hashes |

Holdouts: missing source/evidence access; one altered source after freeze; ambiguous-create cleanup state. Require honest limits, source drift detection and bounded retained exceptions respectively.

## Optimization log and residual risks

Compared a generic full-project review request with the exact activation-gate form by manual contract inspection. Selected the latter; removed reputation/persona filler, separated historical evidence/current candidate and kept eval expectations outside reviewer context. Exact source paths and gate statements are checked during packaging. This prompt has not been run against an external reviewer/model or the holdout set; no evaluation score or external approval is claimed.

The session has no direct Claude channel. Human handoff must supply repository access/attachments. Docker Desktop mount metadata and the first kernel/permission/network assertions remain unexecuted; a reviewer cannot turn their design into runtime proof merely by approving code.

## Amendment prompt refinement

Target: refine the same portable user-message prompt for a second review after the controlling REQUEST CHANGES verdict. Success now requires checking closure of the seam fallback and the exact revised commit/hashes before any image caching or Docker access. Loaded: user review body/attachment, revised connected sources, original/revised evidence and dispositions. Referenced: the six exact input groups in the prompt. Operational resources and author eval notes remain outside reviewer inputs.

Concrete criticism of the original: it had no amendment baseline, could let an old conditional verdict appear to authorize changed code, and did not distinguish the new offline companion proof from actual bootstrap execution. Candidate A was a minimal-diff repair of baseline/counts; candidate B reorganized inputs around revised disposition/manifest and added a focused seam-closure check. Manual contract inspection selected B because it makes the controlling verdict and retained runtime uncertainty explicit. No reviewer/model eval or numeric score is claimed.

Added eval cases: old APPROVE plus later REQUEST CHANGES must preserve the latter; a profile/bundle override without executor must be checked before effects; simulated interruption must not be counted as real container recovery; an expected old-controller failure must not be called a live-daemon reproduction; plural-addon metadata must not certify native-addon denial. Existing cases/holdouts remain. Paths, counts, unchanged-scope statements and frozen diff/hash consistency are checked during packaging; unseen reviewers and drift/ambiguous-create holdouts were not model-tested.

Main prompt changes: two baselines instead of one; explicit superseded approval; new evidence directory; focused regression/companion scrutiny; A–D operational prerequisites; unchanged runtime uncertainty. Human handoff and independent review remain required before real activation.

## Post-create failure prompt refinement

Target: a portable user-message failure review after the one approved runtime invocation. Success is evidence-qualified diagnosis and a minimum next diagnostic/amendment, preserving the mandatory no-retry gate. Loaded: supplied approval/body, actual frozen-run evidence and current connected source. Referenced: five exact input groups in the failure prompt. Runtime/Docker execution, unseen repairs and operational data are outside reviewer authority.

The old activation prompt cannot serve this state: its first-smoke question is consumed, and unit/metadata evidence no longer describes all executed work. Candidate A would merely update its counts/status; candidate B isolates failure evidence and asks for a bounded next design while withholding approval of unseen code. Manual contract inspection selected B. No model benchmark, external prompt run or score is claimed.

Cases checked by inspection: observed extra names must not imply inactive interfaces; cleanup acknowledgement alone must not prove absence; a Docker inspect error must identify the exact missing ID on the verified engine; bootstrap entry must not imply later helper/HTTP/permission checks ran; address-only interface APIs must not prove all devices absent; historical doc hashes must be checked at the approved commit. Holdouts remain missing evidence and forged/drifted runtime sources; no model run against holdouts was performed. Packaging checks validate source equality, hashes, links and one invocation.

Residual limit: no route/flag/address measurements survive because the reviewed bootstrap did not collect them. A new diagnostic or repaired runtime candidate requires a new scoped review before execution.

## Diagnostic candidate prompt

Target: refine the pending failure-design request into a combined failure/evidence review and activation decision for concrete diagnostic source, portable user-message prompt, model unspecified. Success is one bounded diagnostic-enabled smoke decision at exact HEAD/hashes, with unchanged network/permission rules and honest expected-failure semantics. Loaded: current candidate, captured failure, executed offline artifacts, sysfs/Node primary docs. Referenced: five exact input groups in the new prompt. Runtime tooling, root adoption, live data and unseen network-policy repair remain outside reviewer authority.

Compared minimal updates to the old failure-design prompt with a candidate-specific activation prompt. Manual contract inspection selected the latter because the former disallowed approval of unseen code while the source is now concrete. The new prompt performs the pending failure assessment and code review together; it does not claim the failure review has already occurred. No model eval, external channel or score is claimed.

Inspection cases: diagnostic values must not confer admission; denied reads must not cause grant widening; known names must not become an allowlist; fake active metadata must still reach the same rejection; create-ID logging must precede post-create checks; reporter override must retain callable-executor gate; 8-KiB data must survive bounded parent failure text; expected diagnostic FAIL must not become C3/M0 PASS. Holdouts: missing image/evidence, altered source after freeze and namespace/route ambiguity. Paths, hashes, source invariants and executable offline controls are checked during packaging; model holdouts were not executed.

Residual risks: actual sysfs permissions/metadata and diagnostic delivery remain NOT_RUN. The collector cannot establish route absence or namespace provenance. A reviewer may require different bounded diagnostics before any later admission amendment.
