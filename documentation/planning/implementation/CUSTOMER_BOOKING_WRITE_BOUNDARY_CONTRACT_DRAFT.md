## Current behavior and bounded source change

`/api/v1/bookings` is mounted behind authenticate. PUT `/:id` validates params, shared update body, query, then dispatches; DELETE validates params/query before dispatch. Existing middleware uses `stripUnknown:true` and replaces the request value. Malformed HTTP values can therefore produce existing400 before this controller boundary; no route/validator/auth changes are included.

The current handlers call `resolveBookingOwnerScope` and `ensureHRReadOnly`. The former uses `requireBookingActor`, checks exact customer foreign query hints, returns the unchanged signed customer `_id`, and otherwise forwards optional query owner. PUT sends exact users to `updateCustomerNotes` and every other actor to shared `update`. DELETE sends every non-HR actor to shared `delete`. Thus pharmacy/specialist/unknown nonblank roles retain access without a corresponding generic command capability. Presence of a well-shaped token or matching owner hint does not grant that capability.

`BookingService.delete` first calls `getById(id,userId)`, clears reminders, cancels its meeting, attempts the existing slot decrement, and finally invokes `bookingRepository.delete({_id:id})`. The inherited BaseRepository.delete returns `Promise<void>` and ignores the ODM result. BookingModel stores `userId` as required scalar String, and IBooking uses string; use the scalar exact owner predicate, never ObjectId conversion, corporateId, dependentId, pharmacyId or the booking's pre-read owner as a replacement for the supplied scope.

Missing/nonstring/empty/array/object/12-character/nonhex IDs cannot reach an undefined selector or default ObjectId conversion. ## Actor and error order

Existing upstream authentication and Joi/error serialization run first. Within a generic controller handler:

1. Existing `requireBookingActor` through the unchanged resolver requires nonblank string signed `_id` and userType. Missing/invalid/blank values give401 `UNAUTHORIZED` / `Authentication is required`, before all service/repository/provider work. Whitespace-only roles remain401; padded or case-varied nonblank role names are not normalized into a permitted role.
2. For exact `user`, a supplied query owner unequal to the exact signed `_id` retains403 `FORBIDDEN` / `Access to bookings owned by another user is not permitted`, even for a missing resource. Omitted/self query owner returns the exact signed `_id`. No body owner or pre-read owner substitution.
3. Exact HR retains403 `FORBIDDEN` / `HR has view-only access to bookings`, with or without corporate/query hints. Preserve that existing message and position after actor resolution. This is containment of the existing route, not new HR work.
4. Any remaining role other than exact `user`/`admin`, including pharmacy, specialist, lab-like, hospital-like, unknown, padded or mixed-case values, gets403 `FORBIDDEN` / `Access to this booking resource is not permitted`, before any resource lookup or write. Its owner hint cannot grant admission. Missing/owned/foreign IDs have the same controller denial. Do not perform object existence checks or forbidden-field validation before this action denial.
5. Exact users retain their single notes-operation dispatch on PUT and single owner-scoped delete dispatch on DELETE. Exact admin retains shared update and optional query owner, including omitted scope; do not force an admin to own the booking or replace its query owner with signed admin `_id`. Admin privilege remains the legacy allowance, not newly certified clinical/financial authority.

For admitted customer PUT preserve the existing notes method byte-for-byte: malformed scope/body shape guards, one combined owned lookup, hidden404 before field422, then note content400, stored-state409, final owner/status-restricted write and existing final409. Do not send customers into generic update, change its field set or silently translate status changes into cancellation. AR-26 action denial for a forbidden actor precedes any owned-object/field consideration; the already reviewed user notes rule still applies after action admission.

For admitted DELETE, existing `getById(id,userId)` gives404 `BOOKING_NOT_FOUND` / `Booking not found` after exactly one combined lookup when missing or outside a supplied owner scope. This denial precedes reminders, meeting, slots and all delete commands. A valid owner-bound pre-read keeps the current deletion eligibility policy: this draft adds no status/date/payment/clinical/retention denial or cancellation/refund translation. Missing admin optional scope retains legacy lookup behavior. An invalid supplied direct service scope gets401 before reads; `undefined` alone selects its omitted-scope behavior.

A false scoped final result gives409 `BOOKING_DELETE_CONFLICT` / `Booking could not be deleted because it changed`. This safe message echoes no identifier, owner or ODM result. It distinguishes a lost final mutation from the initial hidden404. It covers concurrent deletion/ownership change or any unacknowledged/non-single result and does not diagnose which occurred. Existing error middleware remains unchanged; database errors propagate normally. Controller success remains200 `{success:true,message:'Booking deleted successfully'}` only after awaited service resolution. The retained unscoped branch still ignores its inherited result; this slice makes no result-aware claim for it.

## Effects, concurrency and compatibility limits

After the owned pre-read, retain exactly this existing sequence: awaited clearBookingReminders once; awaited cancelBookingMeet once with reason `Booking deleted`; if slotId exists, existing findById once and conditional decrement once when currentBookings is positive, with the existing caught/logged slot failure; then exactly one final delete command. Preserve current early rejection behavior when reminder/meeting work throws. Preserve cancellation helper's own existing repository/provider behavior; do not relabel a Meet call as zero DB/provider effects merely because the final delete has not run.

The scalar-type restriction applies to the final delete only: the retained getById query can still match a dirty legacy userId array containing the owner and permit the earlier effects before the final guard misses. That pre-read/effect exposure remains open and must not be reported as an initial404 or zero-effect denial. The repository ID guard is a direct-entry invariant; the service retains its existing getById ID/error handling and HTTP retains route-level ID validation. It does not add a new service prefetch-ID policy. The new predicate prevents the final delete from removing a document whose owner no longer matches the supplied scalar scope. It does not protect the earlier reminder/meeting/slot effects against an ownership/state change after pre-read, make effects and deletion atomic, roll them back, fix refund correctness, prevent every ABA/remove-recreate case, add optimistic versions or establish clinical retention. A final409 can follow those earlier effects. An unacknowledged response is not proof no deletion occurred. Do not claim whole-operation zero effects or retry safety for final conflicts. This intentionally small increment preserves existing delete policy/order while improving the mutation boundary; those remaining risks need a separate reviewed command/recovery contract.

Specialist PATCH `/api/v1/specialists/me/appointments/:id/status` remains available through requireSpecialist, its existing validation/controller, and SpecialistPortalService.updateAppointmentStatus. That service reads the booking and requires consultation type plus specialist ownership before calling shared BookingService.update without customer scope. Keep this entire path and shared update byte-identical. Generic PUT/DELETE denials must not be implemented inside shared update or its DTO. Dedicated status/cancel/refund/clinical behavior remains uncertified by this preservation.

Pharmacy creation/payment/client surfaces and dedicated specialist commands are unchanged. Legacy pharmacy/specialist/unknown clients using generic PUT/DELETE intentionally lose that route capability; document the403 without inventing a replacement generic permission. Existing legitimate user notes, user owned DELETE, admin optional-scoped writes and direct shared-service callers remain. Supported-client inventories/tests and current membership/revocation/issuer/dependent authority remain separate acceptance work. Raw unknown fields can still be stripped before these guards; this draft does not claim complete raw-input AR-26 conformance.
