Owner resumed the narrowed customer milestone on 13 November 2026. Base: `9c8d1d8`; legacy reference: `ewa_backend` `origin/integration/perks-v2-combined` `2347787`. No login/dependency/start changes. This document is an implementation contract, not execution admission or runtime acceptance.

## Required behavior

- Only signed individual owner or admin can cancel. Check owner again in each final write, with scalar stored ownership. Pending/confirmed bookings can cancel; completed bookings cannot. Match the legacy paid-only customer cutoff; unpaid cancellation does not require a future appointment.
- Cancellation and its internal-wallet refund, ledger, coupon usage reversal, local slot release and follow-up restoration commit in one transaction on the same database connection. Persist a versioned cancellation settlement marker. No provider, notification, reminder or meeting call occurs in the transaction.
- Derive money only from the booking's matching payment (context, booking ID, user) and completed wallet debits. Require finite nonnegative safe money values. Do not label an unpaid/zero-money cancellation refunded. The existing destination is the internal wallet, explicitly recorded, not an original-instrument gateway refund.
- Serialize competing cancellation and ordinary payment confirmation on the booking and payment records. Use atomic wallet adjustments: compare-and-set the observed balance to the exact paise-derived result in the same transaction, or an equivalent exact atomic increment. Repeated cancellation with a trusted settlement marker can recover any newly observed captured payment without releasing the slot/coupon twice. Do not resurrect cancelled bookings or overwrite refunded payments after a stale gateway read.
- The same fence covers initial/retry wallet deductions, direct-paid setup, gateway order attachment and coupon counting. An in-progress setup may return a retryable cancellation conflict; a failed setup must retain an explicit recoverable state. No `_id`-only setup update may reconfirm a cancelled booking. Count/reverse coupons only with a trusted per-booking applied marker; paid status alone is not that marker.
- Money is existing INR major units converted exactly to nonnegative safe integer paise with at most two decimal places. Reject unsupported currency, nonfinite/negative/unsafe values and mismatched payment/debit provenance. A paid booking with missing or inconsistent funding is reconciliation-required, not a zero-money refund.
- At the existing server coupon-calculation boundary only, round its finite nonnegative derived discount once using the existing gateway convention `Math.round(discount * 100)`, bound it by the validated purchase paise, and derive final paise by subtraction. This preserves normal percentage-discount bookings without rounding or legitimizing corrupt stored balances. Setup-managed free bookings remain pending until paid setup actually commits, so a setup failure can retry.
- New booking creation reserves slot capacity and inserts the booking in one transaction, recording whether this booking holds a reservation. Cancellation releases only that recorded hold. Legacy bookings without sufficient local-effect/financial provenance return an explicit reconciliation-required conflict rather than crediting or releasing guessed quantities. Positive newly created bookings must remain usable.
- A refund/ledger/payment/local-effect failure aborts the transaction and remains retryable; do not swallow it or claim success. Already-cancelled legacy rows with untrusted ledger/slot state are reconciliation-required. Generic admin status updates cannot bypass the dedicated cancellation command to invent refunded truth.
- Generic booking DELETE must not bypass cancellation/refund/audit retention. Route it through the dedicated cancellation semantics or return a clear dedicated-command conflict while retaining the record. Rescheduling moves the explicit slot hold and the booking's slot/date/time atomically, or returns a reconciliation conflict for unproven legacy holds; later cancellation cannot release a different booking's capacity.
- Postcommit reminder/meeting cleanup is retried by subsequent cancellation calls. External effects and notifications are not represented as exactly-once; do not introduce an outbox/framework in this increment. Cancellation response remains truthful if these effects fail.
