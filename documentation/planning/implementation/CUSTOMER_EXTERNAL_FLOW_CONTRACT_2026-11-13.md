## Source contract

- Add authenticated owner/admin local booking detail using the existing sanitized list DTO. Query signed scalar ownership, return own404 for missing/foreign records. Omitted integration in lists means both existing providers, consistently across paginated/unpaginated paths; explicit integration remains honored.
- One `ExternalBookingLocalOperations` adapter owns versioned private `localEffects`: same-connection transactions, revisions, setup expiry, wallet debits/refunds, bound payment/coupon IDs, cancellation intent and provider attempt/acknowledgement. Requests cannot supply this authority. Exclude internal fields from public results.
- `createDraft`, `beginSetup`, `debitWallet`, `attachPayment`, `endSetup` protect initial/retry/direct-paid/order linking. Capture and cancellation cannot resurrect a cancelled/requested booking. INR uses shared exact safe-paise validation; normalize server-derived coupon fractions once at the payment boundary.
- `beginProvider(id,paymentId?)` records the durable attempt before network and returns `{booking, token, shouldFulfill}`. Zero-price server-created bookings require no invented payment. `recordProviderResult(id,token,patch)` accepts only allowed fields for that exact attempt and marks payment processing only after success. `failProvider` records an unknown outcome; timeout/missing ID never proves no provider attempt. Late server provider IDs after cancellation become explicit cancellation obligations, never reactivation.
- `requestCancellation` records signed owner/admin intent and invalidates setup. Shared legacy paid-only IST cutoff applies. A server timeout may separately record system cancellation intent; no user-supplied or unsigned webhook field grants that authority. Genuine server cancellation calls occur outside the transaction. Only their exact attempt token may acknowledge provider cancellation. Unknown outcomes persist as pending/reconciliation and cannot return false completion.
- `settleCancelled(id,owner?)` requires persisted authorized intent plus proven no provider attempt or genuine server cancellation acknowledgement. In one transaction it credits the actual wallet, writes its ledger, settles matching payments, reverses only trusted applied coupons and commits booking/refund state. Repetition credits only new captured funding. Match owner/context/currency/units/debit provenance; reject bounded-history overflow, inconsistent legacy refunds/markers or unknown coupon provenance with reconciliation409.
- Every current refund caller uses the same adapter: explicit cancel, timeout, webhook and PaymentService terminal-failure paths. Unsigned callbacks may record untrusted observations/reconciliation only; they cannot fabricate provider acknowledgement, create trusted cancellation/financial markers, credit money or publish reports.
- Freeze shared PaymentService API before integration: `completeExternalBookingAfterPayment(payment, repository, labstack, healthians, token)` receives a required fifth attempt token; PaymentService calls `beginProvider` before provider work, `failProvider` on error and never independently writes external wallet/coupon/refund state. `settleCancelled` returns an internal booking; its private cumulative refunded paise is not a public DTO.
- A captured, bound payment commits the booking's paid state before provider work; unknown fulfilment remains pending confirmation. Gateway-only refunds create a missing customer wallet in the same settlement transaction, subject to the existing native unique-owner-index requirement.
- Cancellation acknowledgement requires an explicit known cancellation status in the genuine raw provider response, with no declared failure and any supplied reference matching the exact called reference. A normalized fallback status or unsigned callback cannot authorize it. `acknowledgeProviderCancellation(id,token,expectedExternalBookingId)` checks the stored current reference; late provider results clear prior acknowledgement.
- `beginReschedule(id,actor,expectedExternalBookingId)` rejects a changed provider reference between the initial read/slot lookup and admission. Provider result metadata admits the existing LabStack address (at most 4096 characters) and finite latitude/longitude within geographic bounds alongside the existing external payload; no arbitrary metadata becomes authority.
- Existing payment-detail receipts retain the DTO with additive `refund.destination: 'internal_wallet' | null`. Selected and bounded all-attempt records must match ID/owner/external-booking context/INR/paise; consistent duplicate IDs count once, overflow or contradictory state needs reconciliation. Actual gateway charges count only paid/refunded Razorpay attempts, with completed own wallet ledgers counted separately; pending payable amounts are not charges. Reads remain sequential and do not prove a native consistent snapshot.
