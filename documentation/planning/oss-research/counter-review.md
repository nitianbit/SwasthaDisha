# Independent counter-review of open source selection

Reviewed: 2026-11-08. Task F. Scope: `OPEN_SOURCE_OPTIONS.md` against all four clinical, commerce, platform and supplementary notes. This is a review of evidence and recommendations, not a deployment, runtime test, dependency audit, legal certification or 100 RPS benchmark. No source import or application edit was performed.

**Outcome:** the adoption hierarchy is supported as a set of proposed trials. No checked evidence requires reversing the principal exclusions or claiming an immediate full-repository merge is safe. Three specific design decisions should be made more explicit in the synthesis; selected-version and operational gaps remain implementation gates. Confidence is high in the inspected text/metadata and medium in the recommended product fit.

## Substantive issues and opposing interpretations

| ID / severity | Exact conclusion or rule challenged | Evidence and opposite view | Recommended resolution / status |
| --- | --- | --- | --- |
| CR01 / High implementation gate | “Evaluate ERPNext plus Marley as one separate business/clinical stack”; trial requires an “isolated second business.” | Clinical notes A04 document Frappe sites with separate databases. Commerce notes explicitly warn that a multi-company label is not tenant isolation. A single shared site may simplify administration but could share records, permissions, numbering and backup/export boundaries in ways that do not match independent vendors. A site per business can improve the boundary but adds provisioning/upgrades/operations. The current trial says test isolation, without naming the topology decision. | Add an explicit trial decision: site per independent business versus a proven shared-site isolation model; document organization/branch mapping and backup/export boundaries. Do not infer SaaS isolation from ERP companies. **Parent edit recommended; not evidence that ERPNext cannot work.** |
| CR02 / High implementation gate | Money authority row: “Distinct invoice, receipt, attempt, refund, credit, commission, subscription fee and payout records; immutable references and reconciliation.” | This lists records, but does not name who issues/owns each financial mutation. Marley appointment documentation links its own sales invoice; ERPNext supplies accounts while Jansetu already verifies gateway payments and refunds. Two independent invoice creators or refund issuers could produce duplicate documents or financial effects despite correct IDs. Stock authority is much clearer in the report. | Strengthen the money rule: assign invoice issuer/numbering, receivable/payment ledger, gateway verification, credit/refund and payout owners per business/channel; other systems send idempotent commands or hold projections. Reconciliation alone must not authorize duplicate mutations. **Parent edit recommended.** |
| CR03 / Medium selection caveat | “Refine Core … Preferred panel trial.” | Platform notes C10–C12 establish React/TypeScript functionality and MIT Core. The integration baseline reviewed is a backend; it does not establish the actual frontend team's framework, existing panel architecture, design system or API data-provider fit. Refine may save panel work, but adopting it could create a second frontend stack or require substantial adapters. react-admin has the same React prerequisite. | Condition preference on React/frontend-team fit and a bounded API adapter trial. Compare required custom clinical code before selecting. **Parent edit recommended; existing medium-confidence/trial language already prevents claiming a completed panel.** |
| CR04 / Medium release gate | CASL's declared peer range includes Mongoose 6.6; BullMQ current source/docs provide PostgreSQL. | Verified source manifests support both statements. However CASL's inspected adapter source declares `@casl/ability ^7.0.0`; no published version pair or TypeScript 5.4 build was tested. BullMQ's inspected branch manifest and source do not prove which published release ships the PostgreSQL backend. PostgreSQL also introduces a new database; Redis introduces a new queue store. A hardened Mongo queue may cost less. | Keep compatible published-version pinning, baseline build repair and native queue comparison as hard pass/fail gates. No “drop-in,” throughput or migration-time promise. **Resolved by existing qualifications; retain as unresolved adoption work.** |
| CR05 / Medium license/operations gate | OpenELIS is an MPL2 advanced LIS candidate; Bahmni is a mixed-license hospital alternative. | Current Global root license is MPL2; Bahmni's official component policy separately lists its OpenELIS lineage under AGPL3. These are different source/distribution contexts. A future package could include optional services, binaries, modules, terminology/data and dependencies outside a root LICENSE review. An MPL label on one repo cannot approve a whole clinical deployment. | Pin the exact distribution/components and collect complete license/notices/dependency records before import/deployment. A small native lab panel remains a plausible lower-cost choice. **Resolved at research level by mixed-license and full-inventory caveats; dependency audit still open.** |
| CR06 / Medium maintenance caveat | Cal.diy and HospitalRun are poor new SaaS foundations. | Cal.diy's MIT license does permit commercial reuse subject to its terms; its README's personal/non-production recommendation is a support/suitability warning, not a new license prohibition. HospitalRun's checked umbrella/frontend/server repositories are archived, but this does not prove every independent fork or historical component is unusable. | Keep them as bounded workflow references rather than making absolute commercial-use bans or universal claims about all forks. **Resolved by current recommendation wording.** |

These issues do not establish that native implementation is always cheaper. A supported ERP/LIS can save substantial workflow design and maintenance if it passes the same tenant, finance, recovery and operating-cost checks. No source evidence here quantifies that saving.

## Count, citation and recency audit

The **35 distinct project** count is correct: platform 10 + commerce 9 + clinical 10 + supplementary 7 − ERPNext duplicate 1 = 35. Marley is a separate companion application; `frappe/health` is its historical alias, not another project. SENAITE core/UI, Open Hospital distribution/core and HospitalRun umbrella/subprojects are grouped by product. uniCenta is a project examined through its official source archive route; the count does not mean 35 verified GitHub repositories or 35 approved imports.

The four notes distinguish official/public upstream evidence from the user-owned integration baseline. Diverse domains mostly represent official documentation hosting, not independent implementation validation. Root-license facts and feature marketing are qualified; source versions and full dependency sets remain open. The synthesis uses observed dates and does not portray head/push timestamps as release quality. Odoo 20.0 default versus 19.0 feature sources, ERPNext development requirements, BullMQ source-versus-release and GNU Health/uniCenta missing license artifacts are explicitly disclosed. The synthesis correctly avoids a measured savings or 100 RPS claim.

Final publication should ensure the linked unified citation registry exists, retains these spot checks or their corresponding approved records, and the PDF is regenerated from the revised synthesis. The counter-review does not independently certify every upstream feature or dependency.

## Lead disposition after review

CR01–CR03 were addressed in the final synthesis: business authority explicitly requires a Frappe site topology/isolation and operating-cost decision; the money row names invoice issuer and payment/refund/ledger owners; Refine preference is conditional on React/frontend fit. These are now explicit trial gates, not completed implementations. CR04–CR06 remain qualified adoption checks. The separate commerce fact-check also replaced the unsupported implication that most default heads were development branches with the precise statement that default-branch snapshots are not selected stable releases.
